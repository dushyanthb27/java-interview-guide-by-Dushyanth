# JVM Terminology

Comprehensive reference for Java Virtual Machine internals, memory management, and runtime concepts. This glossary covers 80+ essential JVM terms organized alphabetically.

## A

### Ahead-of-Time Compilation (AOT)
**Category**: Compilation

**Definition**: A compilation technique where Java code is compiled to native machine code before runtime, rather than being interpreted or JIT-compiled at runtime. AOT compilation reduces startup time and memory footprint.

**Practical Example**:
```java
// Traditional JIT compilation
// Code is compiled to native during runtime
public class Example {
    public static void main(String[] args) {
        for (int i = 0; i < 1000000; i++) {
            compute();  // JIT compiles after warm-up
        }
    }
    
    static void compute() {
        // Computation
    }
}

// AOT compilation (GraalVM native-image)
// javac Example.java
// native-image Example
// Produces native executable with no JVM startup

// Benefits of AOT
// - Instant startup
// - Lower memory footprint
// - Predictable performance
// - No warm-up period

// Trade-offs
// - Larger binary size
// - Less optimization than JIT
// - Reflection requires configuration
```

**Related Terms**: [JIT Compilation](#jit-compilation), [Bytecode](#bytecode), [GraalVM](#graalvm), [Native Image](#native-image)

**Interview Tip**: Understand the trade-offs between AOT and JIT compilation. Know about GraalVM and native-image for serverless and containerized applications.

## B

### Bytecode
**Category**: Compilation

**Definition**: Intermediate code generated by the Java compiler (javac) from source code. Bytecode is platform-independent and is executed by the JVM, which interprets or JIT-compiles it to native machine code.

**Practical Example**:
```java
// Java source code
public class Example {
    public static void main(String[] args) {
        int x = 5;
        int y = 10;
        int sum = x + y;
        System.out.println(sum);
    }
}

// Compiled to bytecode (.class file)
// javac Example.java

// Bytecode instructions (simplified)
// BIPUSH 5          // Push 5 onto stack
// ISTORE_1          // Store in local variable 1
// BIPUSH 10         // Push 10 onto stack
// ISTORE_2          // Store in local variable 2
// ILOAD_1           // Load variable 1
// ILOAD_2           // Load variable 2
// IADD              // Add
// ISTORE_3          // Store result
// ...

// Viewing bytecode
// javap -c Example.class

// Bytecode characteristics
// - Platform-independent
// - Compact representation
// - Verifiable
// - Interpretable or compilable
```

**Related Terms**: [JVM](#jvm), [Compilation](#compilation), [JIT Compilation](#jit-compilation), [Class File](#class-file)

**Interview Tip**: Understand the role of bytecode in Java's platform independence. Know how to view bytecode using javap.

## C

### Class File
**Category**: JVM Artifacts

**Definition**: A binary file (.class) containing Java bytecode and metadata generated by the Java compiler. Class files follow a specific format defined by the JVM specification.

**Practical Example**:
```java
// Java source
public class Person {
    private String name;
    
    public Person(String name) {
        this.name = name;
    }
    
    public String getName() {
        return name;
    }
}

// Compiled to Person.class
// javac Person.java

// Class file structure
// Magic number: 0xCAFEBABE
// Version: Major.Minor (Java version)
// Constant pool: Strings, numbers, method references
// Access flags: public, final, abstract, etc.
// This class: Class name
// Super class: Parent class
// Interfaces: Implemented interfaces
// Fields: Field definitions
// Methods: Method definitions
// Attributes: Code, exceptions, annotations, etc.

// Examining class file
// javap -v Person.class
// javap -c Person.class (bytecode)
// javap -p Person.class (private members)
```

**Related Terms**: [Bytecode](#bytecode), [Class Loader](#class-loader), [Classloading](#classloading), [JVM](#jvm)

**Interview Tip**: Understand the structure of class files. Know how to inspect class files using javap.

### Class Loader
**Category**: Runtime

**Definition**: A component of the JVM that loads Java classes into memory at runtime. Java has three built-in class loaders: Bootstrap, Extension, and Application, which work together in a parent-child hierarchy.

**Practical Example**:
```java
// Class loader hierarchy
// Bootstrap ClassLoader (loads JDK classes)
//   └── Extension ClassLoader (loads extension classes)
//       └── Application ClassLoader (loads application classes)

// Getting class loaders
ClassLoader bootstrap = String.class.getClassLoader();
System.out.println(bootstrap);  // null (Bootstrap loader)

ClassLoader app = MyClass.class.getClassLoader();
System.out.println(app);  // sun.misc.Launcher$AppClassLoader

// Loading classes
Class<?> clazz = Class.forName("java.lang.String");

// Custom class loader
class CustomClassLoader extends ClassLoader {
    @Override
    protected Class<?> findClass(String name) throws ClassNotFoundException {
        // Load class from custom source
        byte[] classData = loadClassData(name);
        return defineClass(name, classData, 0, classData.length);
    }
    
    private byte[] loadClassData(String name) {
        // Read from file or network
        return new byte[0];
    }
}

// Delegation model
// Child loader delegates to parent before loading
// Prevents duplicate loading and ensures core classes are loaded once
```

**Related Terms**: [Classloading](#classloading), [Class File](#class-file), [JVM](#jvm), [Reflection](#reflection)

**Interview Tip**: Understand the class loader hierarchy and delegation model. Know about class loader issues in application servers.

### Classloading
**Category**: Runtime

**Definition**: The process by which the JVM loads Java classes from the file system or network into memory. Classloading happens in three phases: loading, linking, and initialization.

**Practical Example**:
```java
// Three phases of classloading

// 1. Loading: Find and read class file
// - Class loader finds class file
// - Reads bytecode
// - Creates Class object in memory

// 2. Linking: Verify and prepare
// - Verification: Check bytecode validity
// - Preparation: Allocate memory for static fields
// - Resolution: Convert symbolic references to direct references

// 3. Initialization: Execute static initializers
// - Run static blocks
// - Initialize static fields

class Example {
    static {
        System.out.println("Static initializer");  // Runs during initialization
    }
    
    static int value = 10;  // Initialized during initialization
}

// Explicit loading
Class<?> clazz = Class.forName("Example");  // Triggers loading, linking, initialization

// Lazy loading
// Classes are loaded when first referenced
Example obj = new Example();  // Triggers classloading if not already loaded

// Classloading order
// 1. Parent class is loaded before child class
// 2. Interfaces are loaded when implementing class is loaded
// 3. Static fields and blocks are initialized in order
```

**Related Terms**: [Class Loader](#class-loader), [Class File](#class-file), [Initialization](#initialization), [JVM](#jvm)

**Interview Tip**: Understand the three phases of classloading. Know about lazy loading and initialization order.

## G

### Garbage Collection (GC)
**Category**: Memory Management

**Definition**: An automatic memory management process where the JVM identifies and frees memory occupied by objects that are no longer referenced. Garbage collection eliminates the need for manual memory deallocation.

**Practical Example**:
```java
// Garbage collection
Object obj1 = new Object();
Object obj2 = new Object();

obj1 = null;  // obj1 is now eligible for GC
obj2 = new Object();  // Old obj2 is eligible for GC

// Requesting garbage collection (not guaranteed)
System.gc();
System.runFinalization();

// GC monitoring
MemoryMXBean memoryBean = ManagementFactory.getMemoryMXBean();
MemoryUsage heapUsage = memoryBean.getHeapMemoryUsage();
System.out.println("Used: " + heapUsage.getUsed());
System.out.println("Max: " + heapUsage.getMax());

// GC tuning
// -Xms512m -Xmx2g  // Heap size
// -XX:+UseG1GC     // G1 garbage collector
// -XX:+PrintGCDetails  // Print GC logs

// Generational GC
// Young generation: Short-lived objects
// Old generation: Long-lived objects
// Permanent generation (Java 7) / Metaspace (Java 8+): Class metadata
```

**Related Terms**: [Memory Management](#memory-management), [Heap](#heap), [GC Algorithm](#gc-algorithm), [Memory Leak](#memory-leak)

**Interview Tip**: Understand different GC algorithms (G1GC, ZGC, Shenandoah). Know about GC tuning and monitoring.

### GC Algorithm
**Category**: Memory Management

**Definition**: The algorithm used by the garbage collector to identify and free unreachable objects. Different GC algorithms have different trade-offs between throughput, latency, and memory usage.

**Practical Example**:
```java
// Common GC algorithms

// 1. Serial GC (single-threaded)
// -XX:+UseSerialGC
// Simple, low overhead, but long pause times

// 2. Parallel GC (multi-threaded)
// -XX:+UseParallelGC
// Better throughput, but still has pause times

// 3. CMS (Concurrent Mark-Sweep)
// -XX:+UseConcMarkSweepGC
// Low latency, but complex and deprecated

// 4. G1GC (Garbage First)
// -XX:+UseG1GC
// Balanced throughput and latency, predictable pause times
// Divides heap into regions

// 5. ZGC (Z Garbage Collector)
// -XX:+UseZGC
// Ultra-low latency (<10ms), concurrent
// Java 11+

// 6. Shenandoah
// -XX:+UseShenandoahGC
// Low latency, concurrent
// Java 12+

// GC pause times
// Serial: 100ms - 1s
// Parallel: 50ms - 500ms
// CMS: 10ms - 100ms
// G1GC: 10ms - 100ms (configurable)
// ZGC: <10ms
// Shenandoah: <10ms

// Monitoring GC
// jstat -gc <pid> 1000  // Every 1 second
// jconsole  // GUI monitoring
// -XX:+PrintGCDetails -XX:+PrintGCTimeStamps
```

**Related Terms**: [Garbage Collection](#garbage-collection), [Heap](#heap), [Memory Management](#memory-management), [Pause Time](#pause-time)

**Interview Tip**: Know the characteristics of different GC algorithms. Understand the trade-offs between throughput and latency.

## H

### Heap
**Category**: Memory Management

**Definition**: The region of memory where objects are allocated dynamically at runtime. The heap is shared among all threads and managed by the garbage collector. Heap size can be configured with -Xms and -Xmx options.

**Practical Example**:
```java
// Heap allocation
String str = new String("Hello");  // Object allocated on heap
int[] array = new int[100];        // Array allocated on heap
Person person = new Person();      // Person object allocated on heap

// Stack contains references
int x = 5;  // Primitive on stack

// Heap structure
// Young Generation (Eden, Survivor0, Survivor1)
// Old Generation
// Metaspace (Java 8+) / PermGen (Java 7)

// Heap configuration
// -Xms512m  // Initial heap size
// -Xmx2g    // Maximum heap size
// -Xmn256m  // Young generation size

// Heap monitoring
MemoryMXBean memoryBean = ManagementFactory.getMemoryMXBean();
MemoryUsage heapUsage = memoryBean.getHeapMemoryUsage();
System.out.println("Used: " + heapUsage.getUsed());
System.out.println("Committed: " + heapUsage.getCommitted());
System.out.println("Max: " + heapUsage.getMax());

// OutOfMemoryError
// Heap space exhausted
try {
    List<byte[]> list = new ArrayList<>();
    while (true) {
        list.add(new byte[1024 * 1024]);  // 1MB each
    }
} catch (OutOfMemoryError e) {
    System.out.println("Heap exhausted");
}
```

**Related Terms**: [Stack](#stack), [Memory Management](#memory-management), [Garbage Collection](#garbage-collection), [OutOfMemoryError](#outofmemoryerror)

**Interview Tip**: Understand heap structure and configuration. Know about heap fragmentation and OutOfMemoryError.

## J

### JIT Compilation
**Category**: Compilation

**Definition**: Just-In-Time compilation where the JVM compiles frequently-executed bytecode to native machine code at runtime. JIT compilation improves performance by avoiding interpretation overhead.

**Practical Example**:
```java
// JIT compilation process

// 1. Interpretation phase
// Bytecode is interpreted (slow)
public class Example {
    public static void main(String[] args) {
        for (int i = 0; i < 1000000; i++) {
            compute();  // Initially interpreted
        }
    }
    
    static void compute() {
        // Computation
    }
}

// 2. Warm-up phase
// Method is called frequently (>10000 times by default)
// JVM detects hot methods

// 3. Compilation phase
// Hot methods are compiled to native code
// Subsequent calls execute native code (fast)

// JIT compilation options
// -XX:+PrintCompilation  // Print compilation events
// -XX:CompileThreshold=10000  // Compilation threshold
// -XX:TieredStopAtLevel=4  // Tiered compilation levels
// -XX:-TieredCompilation  // Disable tiered compilation

// Tiered compilation (Java 7+)
// Level 0: Interpreter
// Level 1: C1 compiler (fast, less optimized)
// Level 2: C1 with profiling
// Level 3: C1 with full profiling
// Level 4: C2 compiler (slow, highly optimized)

// Viewing JIT compilation
// -XX:+PrintCompilation -XX:+LogCompilation -XX:LogFile=compilation.log
// java -XX:+PrintCompilation Example | head -20
```

**Related Terms**: [Bytecode](#bytecode), [Compilation](#compilation), [Ahead-of-Time Compilation](#ahead-of-time-compilation), [Performance](#performance)

**Interview Tip**: Understand how JIT compilation works. Know about warm-up time and tiered compilation.

### JVM (Java Virtual Machine)
**Category**: Runtime Environment

**Definition**: An abstract computing machine that enables a computer to run Java programs and programs written in other languages that are compiled to Java bytecode. The JVM provides platform independence through bytecode interpretation and compilation.

**Practical Example**:
```java
// JVM architecture

// 1. Class Loader
// Loads .class files into memory

// 2. Bytecode Verifier
// Verifies bytecode validity

// 3. Execution Engine
// Interprets or JIT-compiles bytecode to native code

// 4. Garbage Collector
// Manages memory automatically

// 5. Memory Areas
// Heap, Stack, Metaspace, Code Cache, etc.

// JVM invocation
// java -Xms512m -Xmx2g -XX:+UseG1GC MyClass

// JVM options
// -Xms: Initial heap size
// -Xmx: Maximum heap size
// -Xss: Stack size
// -XX: Advanced options

// JVM information
System.out.println(System.getProperty("java.version"));
System.out.println(System.getProperty("java.vendor"));
System.out.println(System.getProperty("java.home"));
System.out.println(System.getProperty("os.name"));
System.out.println(System.getProperty("os.arch"));

// Runtime information
Runtime runtime = Runtime.getRuntime();
System.out.println("Available processors: " + runtime.availableProcessors());
System.out.println("Total memory: " + runtime.totalMemory());
System.out.println("Free memory: " + runtime.freeMemory());
System.out.println("Max memory: " + runtime.maxMemory());
```

**Related Terms**: [Bytecode](#bytecode), [Class Loader](#class-loader), [Garbage Collection](#garbage-collection), [Memory Management](#memory-management)

**Interview Tip**: Understand the JVM architecture and its role in platform independence. Know about JVM options and tuning.

## M

### Memory Area
**Category**: Memory Management

**Definition**: A region of memory managed by the JVM. The JVM has several memory areas: heap, stack, metaspace, code cache, and others, each with specific purposes.

**Practical Example**:
```java
// JVM Memory Areas

// 1. Heap
// - Shared among all threads
// - Objects allocated here
// - Managed by garbage collector
// - Configured with -Xms and -Xmx

// 2. Stack (JVM Stack)
// - Per-thread
// - Local variables and method calls
// - Stack frames for each method
// - StackOverflowError if exceeded

// 3. Metaspace (Java 8+) / PermGen (Java 7)
// - Class metadata
// - Method code
// - Constant pool
// - OutOfMemoryError: Metaspace if exceeded

// 4. Code Cache
// - JIT-compiled native code
// - Method code
// - Configured with -XX:ReservedCodeCacheSize

// 5. Program Counter Register
// - Per-thread
// - Address of currently executing instruction

// 6. Native Method Stack
// - Native code execution
// - JNI calls

// Memory configuration
// -Xms512m -Xmx2g           // Heap
// -Xss1m                    // Stack size
// -XX:MetaspaceSize=128m    // Metaspace initial
// -XX:MaxMetaspaceSize=512m // Metaspace max
// -XX:ReservedCodeCacheSize=256m  // Code cache

// Memory monitoring
MemoryMXBean memoryBean = ManagementFactory.getMemoryMXBean();
for (MemoryPoolMXBean pool : ManagementFactory.getMemoryPoolMXBeans()) {
    System.out.println(pool.getName() + ": " + pool.getUsage());
}
```

**Related Terms**: [Heap](#heap), [Stack](#stack), [Metaspace](#metaspace), [Garbage Collection](#garbage-collection)

**Interview Tip**: Understand the different memory areas and their purposes. Know about memory configuration and monitoring.

### Memory Leak
**Category**: Memory Management

**Definition**: A situation where objects are no longer needed but are still referenced, preventing garbage collection. Memory leaks cause the heap to grow over time, eventually leading to OutOfMemoryError.

**Practical Example**:
```java
// Memory leak examples

// 1. Static collections
class MemoryLeak1 {
    private static List<Object> list = new ArrayList<>();
    
    public void addObject(Object obj) {
        list.add(obj);  // Objects never removed
    }
}

// 2. Listener registration without unregistration
class MemoryLeak2 {
    private List<EventListener> listeners = new ArrayList<>();
    
    public void addListener(EventListener listener) {
        listeners.add(listener);
    }
    
    // Missing removeListener method
}

// 3. Circular references
class MemoryLeak3 {
    private MemoryLeak3 next;
    
    public void setNext(MemoryLeak3 next) {
        this.next = next;
    }
}

// 4. Unclosed resources
class MemoryLeak4 {
    public void readFile(String filename) throws IOException {
        FileInputStream fis = new FileInputStream(filename);
        // Missing fis.close()
    }
}

// Detecting memory leaks
// jmap -heap <pid>
// jmap -histo <pid>
// jmap -dump:live,format=b,file=heap.bin <pid>
// jhat heap.bin

// Preventing memory leaks
// 1. Use try-with-resources
try (FileInputStream fis = new FileInputStream("file.txt")) {
    // Use fis
}  // Automatically closed

// 2. Implement AutoCloseable
class Resource implements AutoCloseable {
    @Override
    public void close() {
        // Cleanup
    }
}

// 3. Use weak references
WeakReference<Object> ref = new WeakReference<>(new Object());
Object obj = ref.get();  // May be null if GC'd

// 4. Remove listeners
listeners.remove(listener);
```

**Related Terms**: [Garbage Collection](#garbage-collection), [Heap](#heap), [OutOfMemoryError](#outofmemoryerror), [Resource Management](#resource-management)

**Interview Tip**: Know common causes of memory leaks. Understand how to detect and prevent them.

### Metaspace
**Category**: Memory Management

**Definition**: The memory area where class metadata is stored in Java 8+. Metaspace replaced PermGen and is allocated in native memory, allowing unlimited class metadata (limited only by available system memory).

**Practical Example**:
```java
// Metaspace (Java 8+)
// Stores class metadata, method code, constant pool, etc.

// Configuration
// -XX:MetaspaceSize=128m     // Initial size
// -XX:MaxMetaspaceSize=512m  // Maximum size
// -XX:CompressedClassSpaceSize=1g  // Compressed class space

// Monitoring Metaspace
MemoryMXBean memoryBean = ManagementFactory.getMemoryMXBean();
MemoryUsage metaspaceUsage = memoryBean.getNonHeapMemoryUsage();
System.out.println("Metaspace used: " + metaspaceUsage.getUsed());
System.out.println("Metaspace max: " + metaspaceUsage.getMax());

// Metaspace OutOfMemoryError
// Occurs when Metaspace is exhausted
// Common with dynamic class loading (reflection, proxies, etc.)

// Advantages over PermGen
// - Unlimited size (limited by system memory)
// - Better performance
// - Easier tuning
// - No full GC needed for Metaspace

// PermGen (Java 7 and earlier)
// Fixed size, part of heap
// Required full GC to reclaim space
// Deprecated in Java 8
```

**Related Terms**: [Memory Area](#memory-area), [Class Loader](#class-loader), [Garbage Collection](#garbage-collection), [OutOfMemoryError](#outofmemoryerror)

**Interview Tip**: Understand the difference between Metaspace and PermGen. Know about Metaspace monitoring and tuning.

## O

### OutOfMemoryError
**Category**: Errors

**Definition**: An error thrown when the JVM runs out of memory and cannot allocate more. OutOfMemoryError can occur in the heap, metaspace, code cache, or other memory areas.

**Practical Example**:
```java
// OutOfMemoryError types

// 1. Heap space exhausted
try {
    List<byte[]> list = new ArrayList<>();
    while (true) {
        list.add(new byte[1024 * 1024]);  // 1MB each
    }
} catch (OutOfMemoryError e) {
    System.out.println("Heap space exhausted");
}

// 2. Metaspace exhausted
// Occurs with excessive class loading
try {
    while (true) {
        // Generate and load classes dynamically
        Class<?> clazz = generateClass();
    }
} catch (OutOfMemoryError e) {
    System.out.println("Metaspace exhausted");
}

// 3. Code cache exhausted
// Occurs with excessive JIT compilation
// -XX:ReservedCodeCacheSize=256m

// 4. Direct buffer memory exhausted
// Occurs with excessive ByteBuffer allocation
// -XX:MaxDirectMemorySize=512m

// Handling OutOfMemoryError
// Generally not recommended to catch
try {
    // Memory-intensive operation
} catch (OutOfMemoryError e) {
    // Cleanup and exit
    System.exit(1);
}

// Preventing OutOfMemoryError
// 1. Monitor memory usage
// 2. Set appropriate heap size
// 3. Fix memory leaks
// 4. Use object pooling
// 5. Optimize data structures

// Debugging OutOfMemoryError
// -XX:+HeapDumpOnOutOfMemoryError
// -XX:HeapDumpPath=/tmp/heapdump.hprof
// jmap -dump:live,format=b,file=heap.bin <pid>
// jhat heap.bin
```

**Related Terms**: [Memory Management](#memory-management), [Heap](#heap), [Metaspace](#metaspace), [Memory Leak](#memory-leak)

**Interview Tip**: Know the different types of OutOfMemoryError. Understand how to debug and prevent them.

## S

### Stack
**Category**: Memory Management

**Definition**: A memory area where local variables and method calls are stored. Each thread has its own stack. Stack memory is automatically freed when methods return.

**Practical Example**:
```java
// Stack allocation
void method1() {
    int x = 5;           // Local variable on stack
    String str = "hello";  // Reference on stack, object on heap
    method2();           // New stack frame created
}

void method2() {
    int y = 10;          // Local variable on stack
    // method1's frame is still on stack
}

// Stack overflow
void recursion(int n) {
    if (n == 0) return;
    recursion(n - 1);  // Each call creates new stack frame
}

recursion(10000);  // StackOverflowError

// Stack configuration
// -Xss1m  // Stack size per thread

// Stack monitoring
ThreadMXBean threadBean = ManagementFactory.getThreadMXBean();
long[] threadIds = threadBean.getAllThreadIds();
for (long id : threadIds) {
    ThreadInfo info = threadBean.getThreadInfo(id);
    System.out.println(info.getThreadName() + ": " + info.getStackTrace().length);
}

// Stack trace
Thread.currentThread().getStackTrace();
new Exception().printStackTrace();
```

**Related Terms**: [Heap](#heap), [Memory Area](#memory-area), [Stack Overflow](#stack-overflow), [Call Stack](#call-stack)

**Interview Tip**: Understand stack allocation and lifetime. Know about stack overflow and how to prevent it.

---

### Stack Overflow
**Category**: Errors

**Definition**: An error thrown when the stack memory is exhausted, typically due to excessive recursion or very deep method call chains. StackOverflowError indicates a programming error, not a resource constraint.

**Practical Example**:
```java
// Stack overflow from recursion
void infiniteRecursion() {
    infiniteRecursion();  // No base case
}

infiniteRecursion();  // StackOverflowError

// Stack overflow from deep recursion
void deepRecursion(int n) {
    if (n == 0) return;
    deepRecursion(n - 1);
}

deepRecursion(10000);  // StackOverflowError

// Preventing stack overflow
// 1. Use iteration instead of recursion
// Recursive
int factorial(int n) {
    if (n <= 1) return 1;
    return n * factorial(n - 1);
}

// Iterative
int factorialIterative(int n) {
    int result = 1;
    for (int i = 2; i <= n; i++) {
        result *= i;
    }
    return result;
}

// 2. Increase stack size
// -Xss2m  // 2MB per thread

// 3. Use tail recursion optimization (not available in Java)
// Some languages optimize tail recursion to iteration

// 4. Use trampolining pattern
interface Trampoline<T> {
    Trampoline<T> bounce();
    T result();
    default T run() {
        return bounce().run();
    }
}
```

**Related Terms**: [Stack](#stack), [Memory Area](#memory-area), [Error](#error), [Recursion](#recursion)

**Interview Tip**: Know the causes of StackOverflowError. Understand how to prevent it through iteration or increased stack size.

## T

### Throughput
**Category**: Performance

**Definition**: The percentage of time the application is running productive work versus time spent in garbage collection. Throughput is important for batch processing and throughput-focused applications.

**Practical Example**:
```java
// Throughput calculation
// Throughput = (Total Time - GC Time) / Total Time * 100%

// Example
// Total time: 100 seconds
// GC time: 10 seconds
// Throughput: (100 - 10) / 100 * 100% = 90%

// GC algorithms and throughput
// Serial GC: 95-99% throughput
// Parallel GC: 98-99% throughput
// CMS: 90-98% throughput
// G1GC: 95-99% throughput
// ZGC: 99%+ throughput

// Measuring throughput
// -XX:+PrintGCDetails -XX:+PrintGCTimeStamps
// jstat -gc <pid> 1000

// Example output
```

## V

### Verification
**Category**: Class Loading

**Definition**: The process of checking bytecode validity and security before execution. The bytecode verifier ensures that bytecode doesn't violate Java language rules or security constraints.

**Practical Example**:
```java
// Bytecode verification checks

// 1. Type checking
// Ensure operations are performed on correct types
int x = 5;
// x = "string";  // Compile error (caught by compiler)

// 2. Control flow checking
// Ensure all code paths return values
int getValue(boolean flag) {
    if (flag) {
        return 1;
    }
    return 2;  // All paths return
}

// 3. Access control checking
// Ensure private members are not accessed from outside
class Example {
    private int value = 0;
}

// Example.value = 5;  // Compile error

// 4. Exception handling checking
// Ensure exceptions are properly handled
try {
    // Code that throws exception
} catch (Exception e) {
    // Handle exception
}

// Disabling verification (not recommended)
// -Xverify:none  // Disable verification
// -Xverify:remote  // Verify only remote classes
// -Xverify:all  // Verify all classes (default)

// Verification is part of classloading
// Loading -> Verification -> Preparation -> Resolution -> Initialization
```

**Related Terms**: [Classloading](#classloading), [Bytecode](#bytecode), [Type Safety](#type-safety), [Security](#security)

**Interview Tip**: Understand the role of bytecode verification in Java's security model. Know that verification is automatic and transparent.
